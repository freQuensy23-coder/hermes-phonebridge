# PhoneBridge server 0.1.0

Python 3.11+ ASGI factory: phonebridge_server.app:create_app. This package implements docs/contract-v1.md. It never executes commands locally and accepts only named, advertised Android operations. Device identity comes exclusively from the device bearer token. Admin and device tokens are separate authorities. SQLite stores SHA-256 token digests, not recoverable tokens. QR and device bearer secrets are returned only when created.

Required environment: PHONEBRIDGE_ADMIN_TOKEN, PHONEBRIDGE_PUBLIC_URL. Use a randomly generated admin token containing at least 32 bytes of entropy and an HTTPS origin without a path, query, or credentials. PHONEBRIDGE_DB_PATH defaults to phonebridge.sqlite3. PHONEBRIDGE_REVISION is returned unchanged by /healthz. PHONEBRIDGE_ALLOW_INSECURE=true explicitly permits HTTP for isolated CI/emulator use; never enable it for production. The high-entropy requirement cannot be established by string validation alone: the caller must generate a random token.

Run one worker behind an HTTPS reverse proxy which overwrites forwarded client headers. Bind only to loopback and disable access/debug/payload logging. Production launch command:

    python -m uvicorn phonebridge_server.app:create_app --factory --host 127.0.0.1 --port 18940 --workers 1 --no-access-log --ws websockets-sansio --ws-max-size 1048576 --ws-max-queue 8 --ws-ping-interval 20 --ws-ping-timeout 20 --limit-concurrency 256 --timeout-keep-alive 5 --timeout-graceful-shutdown 15

The application enforces limits even when ASGI transport options differ. The transport limits prevent buffering large frames before application validation. The server intentionally keeps authenticated idle phones connected; WebSocket protocol ping/pong detects dead transport independently of application event traffic. Hello must arrive within 10 seconds, body reads and socket writes have 10-second deadlines, and SQLite uses a five-second busy timeout. Database operations run outside the event loop. Authentication, session-generation and revocation checks occur transactionally. Local active sockets close during revocation; a different worker observes persisted revocation at its next bounded poll. Multiple workers share ownership state, but rate buckets and socket hubs are per process; use one worker unless a trusted proxy supplies a coordinated external rate/concurrency boundary.

Defaults: 64 KiB HTTP request bodies; 32 KiB command arguments; 512 KiB result data including screenshot-sized strings; 16 KiB event data; 1 MiB text WebSocket frames; nesting depth 12; 2,048 JSON values; 128 concurrent HTTP requests and device connections; 32 queued outgoing frames; 16-command delivery batches; 256 queued/sent commands per device; 10,000 command records per device; 1,000 lifetime device records; 10,000 pairing records; 10,000 retained events and 50,000 dedup receipts per device; 2 GiB SQLite page quota. Screenshot handlers must downscale/compress to fit the result budget or report a structured failure. Exceeding a limit refuses work rather than evicting live commands or durable dedup receipts. Rate buckets are bounded to 4,096 keys, with 240 HTTP requests/minute/address, 10 pairing/connection attempts/minute/address and 240 frames/minute/device. Authorization is never accepted from query parameters. Origin-bearing sockets must match the configured public origin. Temporary queue/rate/write pressure closes with 1013, oversized frames with 1009, authorization/policy violations with 1008, replacement sessions with 1012 and shutdown with 1001.

WAL, FULL synchronous writes, foreign keys, private database file permissions, secure deletion and transactional single-use claims are enabled. The database directory must be owned by the service user and not group/world writable. Database files and sidecars must not be symlinks; database hardlinks are refused. SQLite transactions are the durability boundary; event acknowledgements are emitted only after commit. Pairing DELETE also revokes its claimed device. Device DELETE fails outstanding commands with DEVICE_REVOKED and invalidates current sessions. Revoked devices are omitted from listing and return 404. Reconnecting replaces the previous session and replays only unexpired queued/sent commands by their original IDs in FIFO insertion order. Android must durably cache completed results and resolve ambiguous non-idempotent dispatches; transport delivery is at least once, not exactly once execution.

Idempotency keys are scoped to a device, and reusing a key with different op/args/TTL returns 409. An identical retry returns the original acceptance receipt with status queued and its original deadline; GET /v1/commands/{id} supplies current status. Queued results, unknown IDs, other-device results, expired results and conflicting terminal results are refused. Identical terminal results are harmless. Result success and error fields must agree. Any result whose outcome is dispatched is persisted with verified false while preserving package and remaining data. Successful native clock commands require a resolved package and are normalized to outcome dispatched, verified false even if a client claims otherwise. A succeeded transport result never establishes that a native clock setting changed.

Events use device-scoped IDs and durable content-correlated receipts. Identical retries are acknowledged without creating a second cursor, including after retained event payload eviction. Conflicting reuse is refused. Cursor paging is ordered and stable across restarts, defaults to 50 and allows 1–100 records. Notification text remains untrusted opaque data. Payloads retain at most seven days; dedup receipts and terminal command/idempotency records retain at most 30 days. Replay/dedup guarantees are bounded by that retention period. Expiry is checked during delivery, results and polling as well as background maintenance.

## Automated GitHub CI only

No tests, linters, scanners, builds, package imports or verification commands were executed while implementing this package. Commands below belong in automated GitHub CI, not in an interactive session. Run from repository root:

    python -m pip install -r server/requirements-dev.txt ./server
    python -m ruff check server
    python -m pytest server/tests -q --junitxml=server-results.xml
    python -m build server --outdir dist
    python -m pip install -r server/requirements-security.txt
    python -m pip_audit -r server/requirements.txt --strict

The existing combined Python job may keep its shared pytest/httpx/ruff/build pins. Installing server/requirements-dev.txt additionally ensures every runtime/test dependency is pinned. The emulator job currently installs uvicorn==0.34.2 explicitly; its owner must replace that with uvicorn==0.54.0 or install server/requirements.txt instead. Apply the production transport flags in the parent-owned service/deployment configuration. Runtime and build dependencies are pinned in pyproject.toml, and requirements.txt records the complete runtime dependency set. The security tool is separately pinned; its own dependency resolution is not a runtime lockfile.

Tests cover strict configuration and wire schemas; hashed-token/permission/WAL guarantees; atomic claims across SQLite connections; ownership, expiry and idempotency; offline persistence and application restart; event receipt restart/retention/cursor paging; capability changes; native dispatched/unverified preservation; active and cross-worker revocation; body/frame/concurrency/rate/queue/deadline limits; installed package metadata; and a real TCP HTTP/WebSocket flow through Uvicorn. These test sources have not yet run. Successful current-head GitHub CI, dependency-audit results, signed release artifacts, deployment/HTTPS validation and Android/OEM evidence remain parent-owned acceptance gates.
