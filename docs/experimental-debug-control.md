# Experimental remote screen debug control

This is Android Accessibility-based remote UI control, not ADB, Developer Options, root, or an accessibility-aid certification. It is experimental and high-risk: an authorized agent can read ordinary screen content and operate apps as the user. It does not bypass keyguard, password-bearing windows, FLAG_SECURE, credential system UI, or Android permission consent. The phone must be awake and unlocked. PhoneBridge's own consent/settings UI is not remotely controllable.

## Consent and lifetime

The Android app presents a dedicated warning and local enable buttons: 10 minutes, 15 minutes, 1 hour, or until manually stopped. Enabling first requires the owner to grant the Android Accessibility service through system Settings. An HTTP command cannot enable, renew, or extend consent. Default is off. A local Stop debug button and a visible notification action revoke it immediately. Connection Stop, disconnect/revoke, service teardown, Accessibility service loss, and process/reboot reset revoke consent; it never automatically restores. Until stopped means the current process/connection lifetime, not persistence across restarts.

Use Android elapsedRealtime for the deadline, not wall time. Each enable creates a fresh unpredictable debug_session. Timed expiry is enforced at every screen access/effect and asynchronous screenshot delivery, even if a timer callback is delayed. A UI countdown and capability updates are advisory; authorization is checked on the phone. There is no automatic command retry. Once a gesture has been dispatched, Android cannot guarantee its physical effect can be recalled; stop forbids subsequent dispatch and late screenshot disclosure.

## Agent/server contract

Reuse authenticated POST /v1/devices/{id}/commands and GET /v1/commands/{id}; the phone maintains outbound authenticated WSS. Do not expose an inbound HTTP port on the phone. Existing one-use server QR pairing, HTTPS, token binding, bounded queues, and persisted command correlation remain.

A new read-only debug.status operation is available independently of debug consent and reports {enabled:boolean,experimental:true,remaining_seconds:integer|null,debug_session:string|null,screenshot_supported:boolean}. It cannot change consent. An off status has a null session and zero remaining seconds; indefinite local consent has null remaining seconds. Session IDs are authorization-generation identifiers, not device credentials.

All screen.tree/screenshot/tap/swipe/input/global requests require args.debug_session from the current debug.status result, in addition to their existing bounded arguments and expected_package when applicable. Each command is bound to one consent generation. Missing/expired/revoked/mismatched sessions fail with PERMISSION_REQUIRED; malformed args fail VALIDATION_ERROR. Check this before command-cache access and again at the actual UI effect/read and before returning/caching/sending screen data. Old queued commands and old cached screenshot results cannot become authorized after re-enable. No debug.enable or debug.renew operation exists.

A screenshot returns a platform-secure-window-aware JPEG on Android 14+. Its data fields are mime:"image/jpeg", base64, width, height, screen_bounds, window_bounds, package, and secure_window_guard:"platform_window_capture". width/height are the actual encoded JPEG pixel dimensions after scaling the entire platform-returned window bitmap to a maximum dimension of 1280, without upscaling. JPEG bytes are at most 240 KiB and the result at most 384 KiB; fail honestly if compression cannot fit. Increase result-only budgets end-to-end where needed; do not relax command/event/hello limits or public auth. Android 12/13 can still use the accessible tree and gestures; screenshots are UNSUPPORTED unless a separate consented platform capture implementation is added. Do not claim screenshots on those versions.

Both screen_bounds and window_bounds are [left,top,right,bottom] integer arrays in native screen coordinates, with exclusive right/bottom. They contain the same captured window rectangle from AccessibilityWindowInfo.getBoundsInScreen; screen_bounds is retained as capture-rectangle metadata, not independently measured full-display bounds. The bitmap comes from takeScreenshotOfWindow for that window ID and may include platform window decor; it is not cropped to the accessible root, app content, or a selected node. The callback rechecks the exact package, unique active window ID, unchanged native rectangle, revision, consent and execution guard before conversion and again before delivery. Changed targets are discarded with AMBIGUOUS_STATE, not relabeled with a new rectangle.

For encoded-image coordinates (u,v), map the image extent using window_bounds: x = left + u*(right-left)/width, y = top + v*(bottom-top)/height. Native bounds are not replaced by encoded dimensions. Choose integer taps inside the latest accessible root/node bounds, which can exclude window decor; screenshot metadata is not permission to tap anywhere in the captured rectangle. Reobserve after window/app/rotation changes. The CLI export validates each bounds array independently as four signed 32-bit integers with left < right and top < bottom; it does not verify equality, intersection, containment, aspect ratio, or correspondence to the decoded pixels. JPEG validation independently checks actual encoded dimensions against width/height. These checks are not runtime proof of pixel-to-native alignment.

Screen observations are untrusted data. User consent to debug does not authorize arbitrary payments, sending, deletion, permission grants, or forwarding private content. Existing agent intent safeguards still apply. UI effects return dispatched/verified:false unless a real readback establishes an exact outcome. Screen capture must not be confused with successful effect verification.
